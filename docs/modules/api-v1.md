# API v1

[Оглавление](../README.md)

Публичный API (#134, #303, #300, #301, #302, #305): вход устройств и токены нативного клиента, текущий пользователь, чтение велосипедов, людей, подписок, журнала, покатушек и комментариев и описание самого контракта. Это не API всего сайта. Личные ответы владельца о покатушках, поиск, рынок и операции записи — отдельные срезы ([#156](https://github.com/grayhex/cola/issues/156)); неподдерживаемое здесь не описано и не обещано. Веб-приложение по-прежнему работает через прежний API под `/api/…`: он не менялся, а общие правила чтения вынесены так, что обе поверхности вызывают один код.

Параметры `GET /api/v1/bikes`. Неизвестный, повторённый или выходящий за границы параметр — 400, а не молчаливое игнорирование.

| Параметр   | Значение                                                                             |
| ---------- | ------------------------------------------------------------------------------------ |
| `scope`    | `public` (по умолчанию) — публичные велосипеды; `mine` — свои, включая приватные     |
| `category` | типы через запятую (не более 50), ключи фильтра витрины, как в `/api/showcase`       |

| `cursor`   | непрозрачный курсор из `nextCursor`; не разбирайте и не собирайте его самостоятельно |

## Вход и граница транспорта

Кто спрашивает, решает [viewer-session.ts](../../lib/viewer-session.ts), и он ничего не знает о Next, cookie и заголовках. Транспорт-адаптер читает свой credential и передаёт `SessionCredential`; модуль отвечает одним запросом, тем же для всех транспортов: сессия существует, не истекла, пользователь не заблокирован. Отметка «последнее использование» обновляется не чаще раза в пять минут.

| Адаптер           | Где                                                                                        | Что делает                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| Браузер, страницы | [auth.ts](../../lib/auth.ts), [viewer.ts](../../lib/viewer.ts)                             | HttpOnly `cola_session` через cookie jar Next; вход и выход; `currentUser()`       |
| `/api/v1`         | [credentials.ts](../../lib/api-v1/credentials.ts), [viewer.ts](../../lib/api-v1/viewer.ts) | Читает `Cookie` или `Authorization: Bearer` обычного `Request`, без `next/headers` |

Сигнатуры `currentUser()`, `currentSessionHash()`, `startSession()` и `endSession()` сохранены, около тридцати вызывающих файлов не менялись. Схема credential входит в ключ поиска: cookie открывает только `kind='browser'`, Bearer — только `kind='device'` с живым токеном доступа. Новый транспорт добавляет вариант в `SessionCredential` и свой адаптер; бизнес-логика чтения велосипедов не меняется.

Чего нет намеренно:

- **Сессию браузера v1 не выдаёт и не продлевает**: вход на сайте остаётся веб-входом, выход `POST /api/auth/logout` завершает и сессию v1. Токены выдаёт только `POST /auth/sessions`.
- CORS не включён. Изменяющие запросы с cookie требуют заголовок `Origin` сайта (403 `forbidden` иначе); Bearer — не «окружающий» credential, `Origin` к нему не применяется. Каждый неподдержанный метод отвечает 405 с `Allow`, неизвестный адрес под `/api/v1` — 404 в формате API, включая сам `/api/v1`.

## Люди и подписки (#300)

`{ref}` — UUID (36 знаков) или **текущий** username (от 3 до 30 знаков, `[A-Za-z0-9._-]`): значения разной длины, поэтому спутать их нельзя. Решение: прежний username из истории переименований ([#71](https://github.com/grayhex/cola/issues/71)) в `{ref}` **не разрешается**, ответ 404; стабильный ключ — `id`, и клиент хранит его, а не username. Неверный по форме `{ref}`, неизвестный id, прежний username и заблокированный человек отвечают одинаково (404 `not_found` с одним сообщением): существование не раскрывается.

| Поле / правило  | Профиль и списки                                                                                                                                                                                                                                                                                                     |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Profile`       | `id`, `username`, `name`, `avatarUrl`, `bio`, `location`, `createdAt`, `counts{bikes,followers,following}`, `relationship`                                                                                                                                                                                           |
| `UserSummary`   | `id`, `username`, `name`, `avatarUrl`, `relationship`                                                                                                                                                                                                                                                                |
| `relationship`  | `{isSelf, following, followedBy, friends}` относительно вошедшего зрителя; у гостя `null`. Заблокированный зритель — гость (его сессии уже нет)                                                                                                                                                                      |
| Не передаются   | почта, настройки, роль, `blocked`, внутренние id аватара и истории; тест проверяет отсутствие запрещённых ключей и `_` в именах                                                                                                                                                                                      |
| Счётчики        | `bikes` — только публичные; `followers` и `following` — без заблокированных людей. Счётчика `friends` в v1 нет (отдельная операция появится вместе со списком друзей)                                                                                                                                                |
| Велосипеды      | `GET /users/{ref}/bikes` — `BikePage`, то же правило видимости, что у `/bikes` ([bike-visibility.ts](../../lib/bike-visibility.ts)), суженное одним владельцем (`ownerId` в `visibleBikePage`). Приватные велосипеды профиля не попадают сюда никому, даже владельцу: свои, включая приватные, — `/bikes?scope=mine` |
| Заблокированные | профиль заблокированного человека и все его списки — 404; заблокированных людей нет в чужих списках подписчиков и подписок                                                                                                                                                                                           |

Пагинация подписок — keyset, `follow.created_at DESC, user.id DESC`: новые сверху, при равном времени больший id. Курсор — тот же непрозрачный `{createdAt (микросекунды), id}`, что у `/bikes`, id здесь — человека. Подписка, добавленная во время просмотра, встаёт перед курсором и ничего не сдвигает; общего количества нет, оно в `Profile.counts`. Запрос поддерживает только `limit` (1–50, по умолчанию 24) и `cursor`; любой другой параметр — 400. Прежние `/api/social/profiles/*` не менялись (OFFSET, `total`, счётчик `friends`).

## Сессии устройств (#303)

Принятое решение (ADR в [#156](https://github.com/grayhex/cola/issues/156#issuecomment-5955509584)): нативный клиент получает пару непрозрачных токенов, привязанную к строке `sessions` с `kind='device'`. Не JWT: приложение — монолит с одной БД, поиск сессии на запрос уже есть, зато отзыв и блокировка действуют мгновенно, без ключей подписи. Ядро — [device-sessions.ts](../../lib/device-sessions.ts), конечные точки — [auth-handlers.ts](../../lib/api-v1/auth-handlers.ts), схема — [050_device_sessions.sql](../../db/050_device_sessions.sql).

| Что                   | Значение                                                                                                                                       |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Токен доступа         | `cola_at_` + 256 бит, 15 минут (`DEVICE_ACCESS_TOKEN_MINUTES`), заголовок `Authorization: Bearer`                                              |
| Refresh-токен         | `cola_rt_` + 256 бит, одноразовый; простой 60 дней (`DEVICE_REFRESH_IDLE_DAYS`), абсолютный предел сессии 180 (`DEVICE_REFRESH_ABSOLUTE_DAYS`) |
| Хранение на сервере   | только SHA-256: `sessions.token_hash` — digest текущего токена доступа, `refresh_hash` и `previous_refresh_hash` — refresh-токенов             |
| Устройств на человека | 20; при 21-м входе завершается сессия, которой дольше всего не пользовались                                                                    |
| Подтверждённая почта  | для входа не нужна, как и в вебе; операции, которым она нужна, спросят её сами                                                                 |

**Вход по коду приложения (#304).** Вместо почты и пароля `POST /auth/sessions` принимает `code` и `codeVerifier` — одноразовый код с ссылки приложения после нативного входа через Яндекс ID и секрет, чей S256-образ приложение отправило в начале ([поток](accounts.md#нативный-вход-приложения-304)). Ровно один способ: обе пары вместе или половина пары — 400. Код тратится любой попыткой; все отказы — один 401 `invalid_credentials`. Бюджеты те же, что у пароля, ключ — код. Ответ тот же `SessionGrant`.

**Вход.** `POST /auth/sessions` с почтой, паролем и описанием устройства (`name`, `platform` = `ios|android|other`, `appVersion`). Те же счётчики `allowAuth`, что у входа на сайте (по почте, по IP за доверенным прокси, общий), те же блокировки; закрытая регистрация входу не мешает. Неверная почта, неверный пароль и блокировка отвечают одинаково (`invalid_credentials`). Токены есть только в этом ответе.

**Обновление.** `POST /auth/sessions/refresh` с `{ "refreshToken": … }`: токен принимается только телом этого запроса, не URL. Одна транзакция с `SELECT … FOR UPDATE` строки сессии; замена токенов — `UPDATE`, а не `DELETE` + `INSERT`: удаление сработало бы как отзыв чат-токенов человека на всех устройствах (`chat_session_removed`).

- Текущий токен: выдаётся новая пара, прежний refresh-токен становится «предыдущим».
- Предыдущий токен в течение 30 секунд после обновления, пока новым токеном доступа не сделан ни один запрос (так узнаётся, что ответ дошёл до клиента): ответ был потерян, клиент повторяет запрос. Выдаётся ещё одна пара, невостребованная прежняя отзывается, срок допуска не продлевается.
- Предыдущий токен в остальных случаях (допуск истёк или новый токен уже использовался): кража или сломанный клиент. Сессия удаляется целиком, в журнал пишется `session_reuse_detected`, а владелец получает уведомление «Токен устройства использовали повторно» ([notifications.ts](../../lib/notifications.ts)). Клиент видит тот же `invalid_token`, что и при любой другой ошибке.
- Токен старше предыдущего неизвестен: `invalid_token`, сессия не затрагивается.
- Параллельные обновления одним токеном решаются по очереди и не дают ложной тревоги: остаётся одна цепочка, действует последняя выданная пара. Поэтому клиент обновляет токены в один поток (single-flight).
- Лимиты обновления отдельны от входа: по IP (за доверенным прокси) и по сессии, 30 за 15 минут.

**Выход и отзыв.** `DELETE /auth/sessions/current` — выйти на этом устройстве; `GET /auth/sessions` и `DELETE /auth/sessions/{id}` — список и отзыв своих сессий (браузеры тоже в списке). Выход везде, смена и сброс пароля, блокировка и удаление аккаунта действуют на устройства теми же запросами, что и на браузеры: приложение получает 401 `invalid_token` и показывает вход. Список устройств кабинета (`/account?tab=account`) показывает и мобильные сессии.

**Ошибки Bearer.** Токен доступа вместе с cookie сессии — 400 `ambiguous_authentication`; токен неверного вида (в том числе refresh-токен или cookie вместо токена доступа) — 401 `invalid_token`; просроченный — 401 `token_expired` (клиент обновляет токены); неизвестный, отозванный или заблокированного аккаунта — 401 `invalid_token` (клиент возвращается ко входу). Оба с `WWW-Authenticate: Bearer error="invalid_token"` по RFC 6750. Негодный токен не превращается в гостя даже на публичных адресах.

**Наблюдаемость.** События `session_created`, `session_refreshed`, `session_revoked`, `session_reuse_detected` пишутся в журнал с `requestId`, id сессии и платформой, без значений токенов; заголовок `Authorization` не попадает в журнал, трекер ошибок и `client-errors`, а токены вида `cola_at_…`/`cola_rt_…` и `Bearer …` вырезает `scrub`.

**Требования к приложениям** (сервер их не проверяет): хранить токены в Keychain (`AfterFirstUnlockThisDeviceOnly`) или Keystore, refresh отдельно от access, не писать токены в резервные копии, логи, аналитику и отчёты о сбоях; обновлять токены в один поток; на неизвестный код ошибки реагировать по статусу.

Чего нет: JWT, нативного входа через внешних провайдеров (A2, [#304](https://github.com/grayhex/cola/issues/304)), регистрации с устройства, push-адресов ([#173](https://github.com/grayhex/cola/issues/173)), сервера авторизации для сторонних приложений, привязки к устройству, мобильного UI.

## Журнал и комментарии (#301)

Чтение журнала и комментариев к велосипеду и записи. Правила видимости не переписаны: журнал читает тот же `journalPublic`, что и страница записи, комментарии — то же `readable()` движка [comments.ts](../../lib/comments.ts), который через `entitySocial("journal")` обслуживает и записи. Веб и v1 вызывают один код; прежние `/api/journal/*` и `/api/community/*` (OFFSET, `page`, `total`) не менялись.

| Что               | Правило                                                                                                                                                                                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Записи велосипеда | `GET /bikes/{id}/journal`. Велосипед должен быть виден зрителю (как в `/bikes/{id}`), иначе 404. Чужому читателю — только опубликованные публичные записи; владельцу — и черновики. Порядок `created_at DESC, id DESC`, курсор keyset                                                   |
| Запись            | `GET /journal/{id}`: 404 для чужого черновика, приватной записи, записи приватного велосипеда, заблокированного владельца и несуществующего id — ответ один и тот же                                                                                                                    |
| `JournalSummary`  | `id`, `kind`, `title`, `excerpt` (начало текста без разметки, до 240 знаков), `status`, `isPublic`, `eventDate`, `mileage`, `createdAt`, `updatedAt`, `bike`, `author`, `likes`, `comments`, `liked`; без полного текста, фото и компонентов                                            |
| `JournalEntry`    | то же плюс `body` (Markdown как есть, клиент рендерит сам), `components` и `photos`. Цены компонентов — только владельцу или если велосипед показывает цены этого раздела                                                                                                               |
| Комментарии       | Только к публичной цели: публичный велосипед или публичная опубликованная запись. Для приватной цели и для недоступной ветки — 404, как и для несуществующей                                                                                                                            |
| `Comment`         | `id`, `parentId`, `author` (или `null`), `body` (или `null`), `createdAt`, `editedAt`, `deleted`, `replyCount`. Скрытый, удалённый и написанный заблокированным автором комментарий — **надгробие** с `author: null, body: null`, пока у него есть читаемый ответ; иначе его нет совсем |
| Ответы            | Одноуровневые (ограничение БД). `CommentThread` = `{comment, replies}` — корень и не более 3 первых ответов; остальные — `GET …/comments/{commentId}/replies` по `(created_at, id) ASC`                                                                                                 |
| Порядок и курсор  | Корни и ответы — старые сверху, keyset `(created_at, id)`; вставка нового комментария во время просмотра ничего не сдвигает. Параметры `limit` (1–50, 24) и `cursor`; любой другой — 400                                                                                                |
| `focus`           | `GET …/comments?focus={commentId}`: глубокая ссылка. Вместо страницы возвращается ветка искомого комментария и `focusPath` (корень → комментарий); `focus` вместе с `cursor` — 400, несуществующий или недоступный — 404 `not_found`                                                    |

Решения. Тексты комментариев и записей отдаются как Markdown/обычный текст без HTML: экранирование — дело клиента. Схема `BikeAuthor` переименована в `Author`, потому что теперь описывает автора и в карточке велосипеда, и в комментарии; релиз API ещё не вышел, поэтому это не ломающее изменение. Список комментариев не требует входа, но неверный Bearer-токен отклоняется и здесь (401), чтобы клиент не принимал просроченную сессию за гостя.

## Покатушки (#302)

Чтение публичных покатушек и планов без раскрытия скрытых координат и мест встречи. Видимость решает один предикат `effectiveRide` ([rides.ts](../../lib/rides.ts)): публичная покатушка публичного велосипеда автора, который не заблокирован; v1 добавляет к нему «не отменена» (`apiRide`). Скрытая, приватная, отменённая, на приватном велосипеде, заблокированного автора и несуществующая покатушка неотличимы: 404 с одним сообщением, **и для самого владельца** — его личный ответ с приватными полями появится отдельной операцией. `{id}` — UUID покатушки (`share_id` годится только для веб-адресов); не UUID — тоже 404.

| Что           | Правило                                                                                                                                                                                                                                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Два списка    | Прежняя сортировка одним `CASE` («планы по ближайшей дате, затем состоявшиеся») для keyset не годится: это два независимых ключа, поэтому два списка. `/rides` — состоявшиеся, `(coalesce(started_at, created_at), id) DESC`: трек без времени стоит по дате добавления. `/rides/upcoming` — планы, `(ближайшая дата, id) ASC` |
| Повторяющиеся | Еженедельная серия — одна карточка на ближайшей дате (`scheduledAt`), отменённые даты серии пропускаются. Ключ сортировки зависит от часов: серия, дата которой прошла между страницами, может встретиться ещё раз уже на дате следующей недели, потерь нет                                                                    |
| `RideSummary` | Карточка списка: `id`, `title`, `status` (`completed`/`planned`), `kind`, `startedAt` или `scheduledAt`, `recurrence`, `hasTrack`, `metrics`, `bike`, `author`, `likes`, `comments`, `liked`, `participants` (только числа). ## Соглашения записи (#305)

Правила для всех операций записи, введённые на самых простых идемпотентных операциях, чтобы следующие срезы не придумывали их заново. Код — [write.ts](../../lib/api-v1/write.ts), [request.ts](../../lib/api-v1/request.ts), [idempotency.ts](../../lib/api-v1/idempotency.ts).

| Правило                  | Что делает API                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Кто пишет                | `writer(req)`: вошедший (401), для cookie — ещё `Origin` сайта (403 `forbidden`); для Bearer `Origin` не нужен и не проверяется. Проверка одна на схему credential, а не в каждом обработчике; отказ раньше любого действия                                                                                                                                                                                                                                                            |
| Переключатели            | `PUT` ставит состояние, `DELETE` снимает; повтор не меняет результат; ответ — итоговое состояние (`liked` и `likes`, `relationship` и `followers`, `saved`). Права, блокировки, транзакции и уведомления — те же сервисы, что у сайта (`vote`, `setFollow`, `setSaved`), поэтому гонка равных запросов даёт одно состояние                                                                                                                                                             |
| Бюджеты                  | Те же окна `rate_limits`, что у сайта (лайки 120, подписки 60 за 15 минут; «сохранить» — бюджет записей журнала, 20: один на оба транспорта). Сверх бюджета — 429 `rate_limited` с `Retry-After` в секундах до конца окна; отказ ничего не меняет                                                                                                                                                                                                                                      |
| Тело                     | Только `application/json` (415 `unsupported_media_type`), не больше лимита операции (413 `payload_too_large`, чтение обрывается на лимите), разобранное и проверенное strict-схемой (400 `invalid_request` с `details`)                                                                                                                                                                                                                                                                |
| Идемпотентное создание   | `Idempotency-Key: <UUID>`; область — человек и запрос (метод и путь); ключ живёт сутки. Ключ и объект пишутся **в одной транзакции**: параллельные запросы с одним ключом встречаются на первичном ключе, второй ждёт первого и получает его ответ (`replayed`); неудачный запрос ключа не оставляет, повтор выполняется заново. Другое тело при том же ключе — 409 `conflict`; не UUID — 400. Срок и ответ хранит таблица `api_idempotency` ([051](../../db/051_api_idempotency.sql)) |
| Оптимистичная блокировка | Изменяемый объект отдаёт `updatedAt` и заголовок `ETag` (дайджест вида, id и `updated_at` с микросекундами: `etagOf`); `PATCH`/`PUT` принимают `If-Match`. Решение: **412** `precondition_failed`, если версия не текущая, **428** `precondition_required`, если заголовка нет, `*` — «любая существующая», слабый валидатор не совпадает никогда. 409 для этого не используется: оно значит конфликт содержания (`conflict`)                                                          |
| Коды                     | Добавлены `email_verification_required` (403, политика подтверждённой почты #139 дословно), `conflict` (409), `precondition_failed` (412), `precondition_required` (428), `payload_too_large` (413), `unsupported_media_type` (415); `forbidden` и `rate_limited` уже были. Набор по-прежнему открыт                                                                                                                                                                                   |

Что не входит. Создание комментариев, велосипедов, записей журнала, покатушек и объявлений и загрузка файлов — срезы W1–W6, которые применят эти правила; в W0 механизмы идемпотентности и `If-Match` закреплены тестами на тестовой операции (создающего публичного запроса ещё нет: ключ без него бесполезен). «Сохранить» объявление рынка появится вместе с чтением рынка (R6). Прежние изменяющие маршруты `/api/*` не менялись: их проверка `Origin` остаётся прежней.

## Видимость

Условия чтения велосипеда определены в одном месте — [bike-visibility.ts](../../lib/bike-visibility.ts) — и используются страницей велосипеда, витриной, `/api/shared/:id`, `/api/showcase` и v1.

| Кто спрашивает          | Публичный велосипед | Приватный велосипед | Велосипед заблокированного владельца |
| ----------------------- | ------------------- | ------------------- | ------------------------------------ |
| Гость                   | виден               | 404                 | 404                                  |
| Другой пользователь     | виден               | 404                 | 404                                  |
| Владелец                | виден               | виден               | 404 (сессии у него уже нет)          |
| Заблокированный зритель | как гость           | как гость           | как гость                            |

Чужой приватный и несуществующий велосипед неотличимы: оба дают 404 с одним сообщением, существование не раскрывается. Значение, не являющееся UUID, назвать велосипед не может и тоже даёт 404.

**Идентификатор — `id` (UUID).** `share_id` не годится: он заменяется при снятии велосипеда с публикации. Адреса `/b/{slug}-{public_id}` остаются адресами веб-страниц.

**Цены.** Владелец видит свои цены и настройки их показа (`priceVisibility`). Остальные получают цену велосипеда и компонентов только если владелец разрешил её показывать, иначе `null`. В список цены не входят.

## Формат ответов

- JSON, camelCase, даты — ISO 8601 UTC, числа PostgreSQL (вес, цены, пробег) — числами, отсутствие — `null`. Цены в рублях, вес в килограммах, пробег в километрах.
- Ответ собирают [mappers.ts](../../lib/api-v1/mappers.ts): каждое поле выбирается по имени. Строка БД и DTO прежнего API не разворачиваются, поэтому новая колонка не попадёт к клиенту случайно. В контракте нет ни одного ключа с `_`, и тест это проверяет.
- Каждый ответ имеет `Cache-Control: no-store` (кроме документа OpenAPI: `public, max-age=300`) и `X-Request-ID` для обращения в поддержку; медленные и упавшие запросы попадают в [мониторинг](../operations/monitoring.md) как у остальных маршрутов.

### Ошибки

Тело ошибки — `{ "error": { "code", "message", "details?" } }`. Клиент ветвится по `code`, `message` — для людей, `details` называет параметр и причину. Набор кодов открыт: неизвестный код обрабатывается по HTTP-статусу. Внутренние ошибки возвращают `internal_error` без SQL и стека; причина записывается в журнал с тем же request id.

| Код                          | Статус | Когда                                                                                     |
| ---------------------------- | ------ | ----------------------------------------------------------------------------------------- |
| `invalid_request`            | 400    | неверный, неизвестный или повторённый параметр; неверный курсор                           |
| `unauthorized`               | 401    | нет входа, cookie-сессия истекла или аккаунт заблокирован; `scope=mine` без входа         |
| `unsupported_authentication` | 401    | схема `Authorization`, отличная от Bearer                                                 |
| `ambiguous_authentication`   | 400    | одновременно cookie сессии и `Authorization`                                              |
| `invalid_credentials`        | 401    | вход устройства: неверные почта или пароль либо аккаунт заблокирован                      |
| `token_expired`              | 401    | токен доступа просрочен: обновите его refresh-токеном; `WWW-Authenticate`                 |
| `invalid_token`              | 401    | токен неизвестен, отозван, неверного вида или refresh-токен не принят; `WWW-Authenticate` |
| `forbidden`                  | 403    | изменяющий запрос с cookie без допустимого `Origin`                                       |
| `rate_limited`               | 429    | слишком много попыток; заголовок `Retry-After`                                            |
| `not_found`                  | 404    | нет такого велосипеда или адреса, велосипед приватный и чужой                             |
| `method_not_allowed`         | 405    | метод, которого у адреса нет; заголовок `Allow`                                           |
| `internal_error`             | 500    | непредвиденный сбой                                                                       |

## Пагинация

Список идёт от новых к старым, ключ — `created_at DESC, id DESC`, страницы — по курсору, а не по номеру. Велосипед, опубликованный во время просмотра, не сдвигает следующую страницу: ничего не повторяется и не пропускается. Если осталось ровно `limit` велосипедов, список заканчивается без пустой последней страницы. Общего количества нет: оно дорого и устаревает между страницами.

Курсор хранит время создания последнего велосипеда в том виде, в каком его выдал PostgreSQL, с микросекундами, и его id. Время через JS `Date` округлилось бы до миллисекунд, и велосипеды, созданные в одну миллисекунду, пропадали бы или повторялись. Курсор лишь указывает позицию: правила видимости применяются к каждой странице, поэтому подделанный курсор ничего не раскрывает. Курсор, который не разбирается, — 400 `invalid_request`.

Сортировка только по новизне. Сортировки по популярности и рекордам, как на витрине, потребуют другого ключа и входят в дальнейшие срезы.

## Эволюция контракта и гигиена (#300)

Генераторы клиентов закрепляют имена схем и перечисления, поэтому после выхода приложений любое такое изменение становится ломающим. Правила, действующие с первого релиза клиентов:

- **Только аддитивные изменения** внутри `/api/v1`: новое поле, операция, необязательный параметр, значение, которое клиент и так обязан допускать. Ломающее изменение выходит как `/api/v2`, `v1` живёт рядом. Клиент игнорирует неизвестные поля.
- **Набор кодов ошибок открыт.** `error.code` в схеме — обычная строка, а не перечисление: новый код не ломает разбор у выпущенных приложений (закрытый enum в Kotlin ломал бы его). Известные сегодня коды перечислены в схеме `ErrorCode`; клиент обязан обработать неизвестный код по HTTP-статусу. Схема `ErrorCode` нарочно ни на что не ссылается (Redocly предупреждает `no-unused-components`).
- **Именованные схемы вместо безымянных вложенных**: `Error` → `ErrorBody` → `ErrorDetail`; в документе нет имён, придуманных генератором (`ErrorError`, `ErrorErrorDetailsInner`), тест это проверяет. Новая вложенная схема сразу получает имя через `named(...)`.
- **Общие 4xx-ответы** (`InternalError`, `NotFound`) вынесены в `components.responses` и подключаются ссылкой; `info.license` указывает на пользовательское соглашение сайта (`/legal/terms`): отдельной лицензии на API нет, условия задаёт соглашение.
- Списки — только keyset-курсор; на домен один предикат видимости; ответ собирают mappers по именам полей (подробнее — «Что дальше»).

## Контракт и OpenAPI

[schemas.ts](../../lib/api-v1/schemas.ts) — единственное место, где контракт записан:

- strict-схемы ответов: поле, которого там нет, к клиенту не придёт, а тесты разбирают ими настоящие ответы;
- схема query-параметров, из которой разбирается запрос;
- реестр именованных схем: из него [openapi.ts](../../lib/api-v1/openapi.ts) собирает `components.schemas`. Документ получает те же поля, что проверяют тесты, поэтому описание и ответы не расходятся.

`GET /api/v1/openapi.json` отдаёт документ OpenAPI 3.1 (JSON Schema 2020-12, его строит `z.toJSONSchema` из Zod, новой зависимости нет). Адрес сервера берётся из `PUBLIC_SITE_URL`/`APP_ORIGIN`, не из заголовков запроса. В схемах описаны auth (`cookieSession`, без Bearer) и ошибки.

### Как добавить операцию

1. Схема ответа в `schemas.ts` через `named(...)`; для списков — параметры в схему query.
2. Mapper в `mappers.ts`, который выбирает поля по имени.
3. Обработчик в `handlers.ts`: authentication, validation, mapper, статус. Правила чтения — в общем service-слое, не в обработчике.
4. `route.ts` под `app/api/v1/` с `traced(...)`; остальные методы — `methodNotAllowed`.
5. Описание операции в `openapi.ts`.
6. Тесты. `api-v1.test.js` сверяет, что операции документа совпадают с файлами `app/api/v1`: документ без маршрута или маршрут без описания не пройдут.

### Клиенты

Документ проверен реальными генераторами; ни один клиент в репозиторий не входит. Результат на `main` @ `893496a` (02.10.2026):

- Redocly CLI: документ валиден как OpenAPI 3.1; осталось три рекомендательных замечания (нет поля `license`, адрес сервера на localhost при выгрузке для проверки, у статичного документа нет 4xx).

Повторено с операциями записи (#305, 03.10.2026): TypeScript-пример клиента (`PUT`/`DELETE` с Bearer без `Origin`, `Retry-After` из 429, `@ts-expect-error` на число вместо id) компилируется `tsc --strict`; Kotlin-клиент (`BikeLike`, `FollowResult`, `SaveResult`) компилируется и разбирает реальные ответы: итоговые состояния лайка, подписки и «сохранить», а также 429 `rate_limited` и 403 `forbidden`. Redocly: валиден, два прежних предупреждения. Не проверено: поведение приложения при потере ответа и повторе на реальной сети.

Повторено с нативным входом (#304, 03.10.2026): TypeScript-пример входа по коду (`code`, `codeVerifier`) компилируется `tsc --strict`; Kotlin-клиент: `CreateSessionRequest` с кодом и без пароля сериализуется без полей `email` и `password` и по-прежнему разбирает прежние ответы. ## Совместимость с прежним API

Прежние endpoints, их DTO и статусы сохранены: `GET /api/me` по-прежнему отвечает `200 {"user": null}` гостю, `GET /api/bikes` отдаёт владельцу его велосипеды, `/api/shared/:id` и `/api/showcase` — прежние ответы. Общие у них с v1 условие видимости (`bike-visibility.ts`), чтение велосипеда по `share_id` или `id`, выборка и сборка карточек (`showcase.ts`) и правило сессии. Владельческий ответ прежнего API по-прежнему разворачивает строку БД; для публичного контракта он не используется.

## Что дальше

Карта следующих вертикальных срезов (пользователи, журнал и комментарии, покатушки, поиск, компоненты, рынок, запись) и принятое решение по токенам мобильного клиента — в [#156](https://github.com/grayhex/cola/issues/156); токены устройств выполнены ([#303](https://github.com/grayhex/cola/issues/303)), срезы чтения выполнены: [#300](https://github.com/grayhex/cola/issues/300), [#301](https://github.com/grayhex/cola/issues/301), [#302](https://github.com/grayhex/cola/issues/302). [#151](https://github.com/grayhex/cola/issues/151) подключает внешние идентичности к границе `viewer-session.ts`, не меняя v1.

Правила, которых придерживаются все следующие операции:

- Контракт меняется только аддитивно: новое поле, операция или необязательный параметр. Ломающее изменение выходит как `/api/v2`. Клиент игнорирует неизвестные поля.
- Набор кодов ошибок открыт: клиент обязан обработать неизвестный `code` по HTTP-статусу, а не падать на разборе.
- Каждый список — keyset-курсор с детерминированным ключом; `?page=`, `OFFSET` и `total` прежнего API в v1 не переносятся. Ключ, который меняется (популярность), описывается отдельно.
- На домен один предикат видимости, общий для веб-страниц, прежнего API и v1; ответ собирают mappers по именам полей.
- Операции записи используют соглашения W0 (см. «Соглашения записи»): проверка Origin — свойство схемы credential, создающие запросы принимают `Idempotency-Key`, изменяемые объекты — `If-Match`; права и политика подтверждённой почты те же, что в прежнем API.
