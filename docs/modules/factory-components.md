# Комплектация и продуктовый каталог (#205, #221)

Resolver, мастер и серверный импорт используют одну чистую функцию нормализации.
Каталожное имя строится из марки, семейства и модели. Размер покрышки, диаметр
ротора, материал, casing и рекламное описание остаются в характеристиках и notes,
полные исходные сведения — в `bikes.factory_spec`.

- Вложенные Front Tire / Rear Tire становятся отдельными установленными деталями.
  `Butcher, GRID TRAIL … 29x2.4` → `Specialized Butcher`, категория «Передняя покрышка»;
  размер сохраняется в описании/attributes. Аналогично Eliminator сзади.
- Canyon: `Canyon Cockpit CP0039` — имя, следующий абзац — описание.
- `Shimano Deore M6100 … 160мм` и `… 180мм` получают одно имя модели.
- `Maxxis Icon 29x2.2 … EXO/TR` → `Maxxis Icon`.
- `Not Available`, `Unspecified`, `None included` не создают установку.
  Безымянное оборудование («интегрированная рулевая», «карбоновые шатуны»)
  сохраняется в комплектации без карточки продукта. Бренд велосипеда не
  угадывается как бренд всех его компонентов.
- HTML entities и лишние разделители очищаются. Значимые обозначения моделей
  (AXS, Di2, SL, суффиксы артикулов) не отбрасываются.

Версия extractor повышена до 5: прежние результаты Resolver не возвращаются
как свежий кеш. Новый поиск может требовать доступа к исходному сайту; rebuild
работает **офлайн из сохранённой комплектации**, без массового повторного парсинга.

## Граница каталога и миграция #221

`components` — установки: собственные ID, исходная категория, название,
примечание, стоимость, ссылка и порядок. `model_id` теперь nullable. Позиция
`position` (front/rear/left/right) выводится сервером из метки установки;
она не участвует в идентичности продукта. Исходные метки сохранены для
комплектации и истории. `component_models.category` — тип продукта:
«Покрышки», «Обода», «Втулки», «Колёса», «Тормоза», «Манетки / дуалы».
Передний и задний переключатели остаются разными продуктовыми типами.

Политика задана в `component-products.js` и миграции
`033_component_products.sql`; тест проверяет их согласованность. Из каталога
исключены каретки, кассеты, звёзды/цепи/ремни, роторы, отдельные тормозные
ручки, рулевые, зажимы, камеры, спицы и неизвестные категории. «Другое» и
произвольная категория не обходят ограничение. В гараже они по-прежнему доступны,
включая настройки иллюстраций.

Автоматическое создание требует допустимого типа и краткого имени с известным
брендом и моделью. Список брендов объединяет Resolver и существующий список
производителей сайта; администратор может дополнить последний. Неизвестный бренд,
описание или один бренд без модели безопасно остаются только в комплектации.
Политика применяется триггером БД ко всем путям записи, включая ручное
редактирование, мастер, импорт и rebuild. Публикация велосипеда сама по себе
не создаёт модели. Админка не позволяет менять продукт на запрещённый тип
или объединять разные типы продуктов.

**При первом deploy выполняется миграция данных; предварительно нужен backup.**
Она сохраняет все установки и factory-spec без изменения содержательных полей,
объединяет допустимые front/rear модели через существующий механизм ссылок,
сохраняет их фотографии/обсуждения и убирает недопустимые модели. Фотографии и
обсуждения удаляемых непродуктовых карточек удаляются, файлы передаются штатной
очереди GC; ссылки рынка на них обнуляются, сами объявления сохраняются.
Ранее выданные URL допустимых парных моделей ведут в общую карточку.
Откат миграции — восстановление backup, не возврат одного старого образа.
Это согласованная в #221 пересборка неценного каталога, а не повторная нормализация #205.

После deploy проверьте /components и комплектации: одна модель спереди/сзади —
одна карточка и две установки; разные модели — две карточки. Spec-only строки
не имеют ссылки на продукт. Повторный импорт/rebuild не возвращает исключённые
карточки. Уже удалённые старым rebuild или пользователем установки не
восстанавливаются предположениями: полная заводская спецификация сохранена отдельно.

## Сохранение ручных изменений при offline rebuild

Мастер по-прежнему позволяет менять и добавлять детали. Сервер хранит собственные
снимки неизменённых импортированных записей в `factory_spec.colaImport`.
Изменённые имя, категория, notes, цена, ссылка или группа не перезаписываются.
Удалённые пользователем детали не воссоздаются. Повторный обычный импорт заполняет
только пустую сборку, как и раньше; снимки происхождения переживают обновление
заводской спецификации.

Для записей до #205 нет надёжного признака происхождения. Rebuild использует
точное совпадение со старой проекцией импорта по всем содержательным полям,
учитывает штатную группу и исключает дубли/неоднозначность. Всё остальное остаётся
нетронутым и перечисляется в `preservedParts`. Если пользователь явно ввёл ровно
тот же текст, что старый импорт, исторически отличить эти случаи невозможно:
поэтому перед применением необходим просмотр конкретного отчёта.

Rebuild обновляет распознанные установки на месте, сохраняя ID и порядок.
При разделении одной строки дополнительная деталь добавляется в конец списка.
Удаляются только относящиеся к старому импорту пустые модели без установок,
фотографий, обсуждений, связей рынка, объединений и административных правок.
Защищённые остатки перечисляются в `retainedModels`: их нужно разобрать вручную.
Снимки журнала, ручные детали и содержимое медиатеки не меняются.
Сам offline rebuild не выполняет миграцию #221; её применяет штатный migration runner.

## Выполнение после приёмки и выкладки

Используйте актуальный ops-образ из этого PR и тот же Compose project/env, что
у работающей установки. Сначала сделайте [штатный backup](../operations/backup-restore.md).
Число велосипедов определяется из БД; старые числа из issue не являются фильтром.

```bash
cd /opt/stacks/cola
sudo docker compose --env-file .env.production -f compose.prod.yaml \
  run --rm --no-deps -T migrate node scripts/rebuild-factory-components.js \
  > factory-components-preview.json
```

Просмотрите `changes` (до/после), `removeModels`, `retainedModels` и
`preservedParts`. Если реальное имя отсутствует во всех сохранённых данных,
rebuild его не выдумывает: безымянное оборудование останется в исходной
спецификации, пригодную модель можно добавить вручную после проверки источника.

После проверки отчёта:

```bash
COLA_REBUILD_FINGERPRINT=$(python3 -c 'import json; print(json.load(open("factory-components-preview.json"))["fingerprint"])')
sudo docker compose --env-file .env.production -f compose.prod.yaml \
  run --rm --no-deps -T migrate node scripts/rebuild-factory-components.js \
  --apply --expect "$COLA_REBUILD_FINGERPRINT" \
  > factory-components-applied.json
```

Применение выполняется одной транзакцией с блокировками. Если между просмотром и
запуском изменились данные, команда завершится `REBUILD_CHANGED` без частичного
применения: получите и проверьте новый отчёт. Отчёты содержат данные сборок;
храните их у оператора вместе с результатом проверки.

Повторите dry-run: `changes` и `removeModels` должны быть пустыми. Проверьте
каталог и все текущие тестовые велосипеды: отдельные покрышки, краткие имена,
сохранённые notes/ручные правки/фото и связи рынка. Наличие `retainedModels` или
неоднозначных старых записей в `preservedParts` требует осмысленной проверки,
а не автоматического массового удаления.

Тесты используют сохранённые HTML fixtures Canyon/Specialized и синтетические
БД; production rebuild и сверка реальных велосипедов выполняются владельцем
после приёмки. Кодовый PR сам по себе не означает, что production уже очищен.
