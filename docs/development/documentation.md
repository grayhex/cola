# Как поддерживать руководство

[Оглавление](../README.md)

## Источники истины

Описание поведения проверяется по маршруту, доменной функции, схеме и тесту на одном commit. Версии пакетов — по package/lock, порты и env — по Compose, порядок миграций — по реальному runner, deployment — по workflow **и установленному wrapper**. Содержимое документации не подтверждает, что конфигурация уже применена на VPS.

Состояние внешнего сайта, цены API и доступные тарифы не фиксируйте как вечные свойства продукта. Дайте официальный источник и отделите fixture от live-проверки. Разовое сетевое наблюдение не является диагнозом для всех установок.

## Структура

`architecture/` объясняет общие границы; `development/` — работу разработчика; `modules/` — продуктовые возможности; `resolver/` — внутренности парсера; `integrations/` — внешние SDK и графику; `operations/` — серверные процедуры. У одной темы один основной документ, остальные ссылаются на него.

Текущие ограничения и требования находятся в соответствующей главе. Завершённые отчёты, промежуточные планы, протоколы ручной приёмки и исторические снимки не хранятся рядом с действующим руководством: их сохраняет Git. При удалении материала сначала перенесите уникальные актуальные требования в существующую главу. Не создавайте дублирующие архивы или заглушки.

## Шаблон описания модуля

```markdown
# Название модуля

[Оглавление](../README.md)

## Назначение
Кто пользуется модулем и за что он отвечает.

## Точки входа
Страницы, основные API, связи с другими модулями.

## Данные и основные функции
Сущности, файл-владелец логики, ключевые функции.

## Сценарий и ограничения
Поток данных, права, ошибки, повторные операции.

## Расширение и проверки
Что менять совместно и какие регрессии обязательны.
```

Ссылки на код относительные, чтобы открываться в той же ветке. Постоянные ключи сущностей отличайте от редактируемых подписей. Реализованное поведение, ограничение и предложение не должны смешиваться.

## Единый комплект

[book.json](../book.json) перечисляет основные главы в порядке чтения. Изменение главы требует синхронно обновить manifest и [оглавление](../README.md). Генератор книги не является runtime-зависимостью приложения.

## Проверка перед PR

Каждая глава manifest должна существовать. Относительные ссылки и изображения должны разрешаться в текущем дереве; при удалении или переименовании исправьте все входящие ссылки вместо создания переходника. Сверьте команды с исходными скриптами и границей host/container.

`git diff --check` проверяет whitespace, но не смысл и не ссылки. Сохраняйте лицензии, используемую приложением графику и функциональные тестовые фикстуры. Скриншоты текущего CI хранятся как ограниченные по сроку artifacts, не коммитятся как исторический альбом.

В описании PR перечисляйте результаты только своего итогового дерева и явно называйте недоступные проверки. Не копируйте числа успешных тестов из прежней ветки.
