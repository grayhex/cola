# Как поддерживать руководство

[Оглавление](../README.md)

## Источники истины

Описание поведения проверяется по маршруту, доменной функции, схеме и тесту на одном commit. Версии пакетов — по package/lock, порты и env — по Compose, порядок миграций — по реальному runner, deployment — по workflow **и установленному wrapper**. Содержимое `docs/` не подтверждает, что конфиг уже применён на VPS.

Состояние внешнего сайта, цены API и имена доступных тарифов не фиксируйте как вечные свойства продукта. Дайте ссылку на официальный источник и отделите лабораторный fixture от live-проверки. Не сохраняйте в текущем runbook разовые «из этой сети сегодня был 403» как диагноз для всех установок.

## Структура

`architecture/` объясняет общие границы; `development/` — работу разработчика; `modules/` — продуктовые возможности; `resolver/` — внутренности парсера; `integrations/` — внешние SDK и графику; `operations/` — серверные процедуры. У одной темы должен быть один основной документ, остальные ссылаются на него.

Старые верхнеуровневые файлы — только указатели. Не дописывайте в них новые инструкции. История прежних решений остаётся в Git, а актуальные ограничения — в соответствующей главе.

## Шаблон описания модуля

```markdown
# Название модуля

[Оглавление](../README.md)

## Назначение
Кто пользуется модулем и за что он отвечает.

## Точки входа
Страницы, основные API, связи с другими модулями.

## Данные и основные функции
Сущности, файл-владелец логики, ключевые функции.

## Сценарий и ограничения
Поток данных, права, ошибки, повторные операции.

## Расширение и проверки
Что менять совместно и какие регрессии обязательны.
```

Ссылки на код относительные, чтобы открываться в той же ветке. Постоянные ключи сущностей отличайте от редактируемых подписей. Пишите явное «реализовано», «ограничение» или «предложение», не смешивая roadmap с контрактом.

## Единый комплект

[book.json](../book.json) перечисляет основные главы в порядке чтения, без compatibility-указателей. Этот список пригоден как manifest для будущей сборки HTML/PDF/Markdown-книги. Изменение файла/главы требует синхронно обновить manifest и [оглавление](../README.md). Сам этот PR не вводит генератор PDF и не добавляет его зависимости в приложение.

## Проверка перед PR

Убедитесь, что каждая глава из manifest существует, относительные ссылки ведут на файл/каталог текущего tree, заголовки и fenced blocks корректны. Проверьте commands против имен параметров в исходном скрипте. `git diff --check` обнаруживает whitespace-проблемы, но не проверяет смысл и ссылки.

Для удаления инструкции укажите, куда перенесена актуальная тема. Для переименования оставьте короткий указатель, если путь уже встречается в README, старых PR или документации сервиса. Не копируйте прежние успешные числа тестов в описание нового изменения.
