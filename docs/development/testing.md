## Команды

Выполняются из корня репозитория после установки обеих групп зависимостей:

```bash
pnpm lint
pnpm typecheck
pnpm test:typecheck
pnpm test
pnpm build
(cd services/bike-resolver && npm run typecheck && npm test && npm run build)
pnpm test:integration
pnpm exec playwright install --with-deps chromium webkit
pnpm test:e2e
python3 scripts/test-compose.py
bash scripts/test-backup-drill.sh
```

Команды — перечень уровней, не требование запускать тяжёлый полный drill после каждой правки текста. CI проверяет полный набор согласно [workflow](../../.github/workflows/check.yml). Узкую регрессию сначала запускайте адресно: `node --test tests/map-settings.test.js` или нужный Resolver fixture.

В смешанной фазе #256 `tsconfig.json` — конфигурация Next и native TS (`strict`, DOM/Node/React, bundler resolution). После #258 весь backend/API проверяется одним strict root typecheck; две backend `jsconfig`-конфигурации удалены. После #260 UI тоже полностью native TSX, production JS baseline пуст; оставшийся флаг `allowJs` и временные migration-механизмы удаляются в #261. `pnpm check:production-ts` отдельно сканирует production-дерево, включая untracked файлы. При миграции удаляйте соответствующий путь из `scripts/production-js-baseline.json`; не добавляйте новые пути. `lib/version.js` — адресное исключение генератора. Для shared TS policy также проверяет совместимость с прямым запуском Node 24 (`stripTypeScriptTypes`, mode `strip`); отрицательная проба запрещает синтаксис, требующий трансформации. CLI использует TypeScript 7 через `@typescript/native`, Next/ESLint — совместимый API TypeScript 6 через npm alias `typescript`; см. [принципы](principles.md).

Для UI без изменений Resolver после production build можно запустить `node scripts/test-ui.js`. Harness поднимает disposable PGlite и Next на 3100, выполняет `gallery-interactions.spec.js` в Chromium и завершает процессы. Браузер должен быть установлен Playwright. Можно передать другие spec-файлы, `--project` и обычные параметры Playwright. Пример: `node scripts/test-ui.js tests/e2e/design.spec.js tests/e2e/navigation.spec.js tests/e2e/garage-polish.spec.js tests/e2e/gallery-interactions.spec.js`. Ни production БД, ни внешний парсер не используются. Unit-регрессии очереди реакций, URL и контраста: `node --test tests/gallery-interactions.test.js`.

После #259 отрицательные пробы `test:typecheck` проверяют также реальные границы UI: props `CompactDialog`, nullable viewer, настройки пользователя и generic API response, пары ключ/значение админских настроек, режимы окон гаража и виды ответа поиска. Велосипеды и каталог покрывают `garage-polish`, `bike-actions`, `bike-heading`, `resolver`, `component-catalog`, `component-dialog`, `component-community`, `component-photo-search`, `component-illustrations`, `gamification`, `legal-editor` и `site-experience`; для поиска комплектаций включайте `UI_TEST_RESOLVER=1`. Core UI покрывают `account-workspace`, `account-security`, `account-recovery`, `navigation`, `motion`, `gallery-interactions` и `accessibility`; для сценариев интеграций кабинета включайте `UI_TEST_ACTIVITY=1` (fixture Ride with GPS).

После #260 отрицательные пробы проверяют также content/feed/save/contact DTO, targets обсуждения, RSVP, preview, телеметрию и отсутствие приватных полей автора и интеграции. Поездки и планирование покрывают `rides`, `ride-intents`, `ride-passport`, `ride-organize`, `ride-agreements`, `ride-home`, `rides-market` и `activity-sync`. Карты и графики дополнительно проверяйте на мобильной ширине, клавиатурой и при reduced motion; fixture Яндекса/Ride with GPS не подтверждает доступность живого провайдера.

Опциональный `COMMUNITY_ARTWORK_DIR` указывает на локальную папку с `bike-1.webp`…`bike-3.webp` для визуального сравнения с реальными публичными ресурсами. Без него тесты создают нейтральные локальные изображения. Это входные данные теста, не новая система управления графикой сайта.

## База и изоляция

[Integration harness](../../scripts/test-resolver-integration.js) создаёт собственные временные БД/каталоги и запускает fixture Resolver. При `TEST_DATABASE_URL` используется отдельный PostgreSQL с правами создания тестовой БД. **Не передавайте production connection string.** Без этой переменной локальный harness может использовать одно соединение disposable PGlite; concurrency-тесты требуют настоящий PostgreSQL.

`tests/community-concurrency.js` удерживает транзакцию лайка после блокировки велосипеда, запускает комментарий на другом соединении и через `pg_blocking_pids` подтверждает пересечение запросов. После освобождения оба запроса должны завершиться, сохранив комментарий и два уведомления. Это регрессия взаимной блокировки: операции соблюдают порядок `users → bikes`, включая внешние ключи уведомлений. Тест подключён к HTTP-набору при использовании PostgreSQL.

В браузерной проверке карты ответы тайлов задерживаются до измерения предпросмотра; затем проверяются неизменная высота, наведение на график и сохранение canvas при прокрутке. Обзор всех страниц открывает каждый URL в отдельной вкладке, чтобы отмена фоновой предзагрузки при замене документа не считалась ошибкой страницы в WebKit. Ошибки JavaScript продолжают проверяться; переходы, история и восстановление прокрутки покрыты отдельным сценарием.

Браузерные тесты меняют настройки сайта, поэтому `workers:1` и отсутствие внутреннего fullyParallel — часть изоляции. CI распараллеливает браузеры по **разным** runners и БД, а не по общей базе. Артефакты разных браузеров/attempt имеют разные имена.

Backup drill создаёт собственные Compose projects и удаляет только их. Это не команда для проверки восстановления поверх рабочего проекта `cola`.

Редактор объявления проверяется с намеренно задержанной загрузкой JavaScript (#162): все SSR-поля и действия заблокированы до гидратации, затем первый ввод сохраняется, фотография получает HTTP 201 и объявление публикуется. Это воспроизводит гонку раннего ввода без случайных задержек, повторов теста или увеличения таймаутов.

## Нулевой бюджет ESLint (#140)

Базовый замер после #126 и #160 на `6a6bfe4b31bec1f20544fa5a2c3bc1a5a7565fa7`: 0 ошибок, 157 предупреждений (68 `no-unused-vars`, 27 `exhaustive-deps`, 26 `no-img-element`, 22 `no-html-link-for-pages`, 12 `no-location-assign-relative-destination`, 2 `no-useless-escape`). После исправлений `pnpm lint` требует 0 ошибок и 0 предупреждений; та же команда выполняется в CI. Новое предупреждение блокирует PR.

Зависимости эффектов описывают реальные причины обновления: идентификатор пользователя, страницу и фильтры, примитивные поля модели. Ответы списков проверяют ревизию запроса; поиск пользователей читает текущий черновик при отправке формы или переходе страницы, без запроса на каждую букву. Списки не должны перезагружаться из-за нового объекта с теми же фильтрами.

Допустимые исключения перечислены рядом с кодом:

- `useBikeReaction` сохраняет одну очередь запросов на велосипед и пользователя, даже если список вернул новый объект того же велосипеда. Локальное исключение `exhaustive-deps` защищено браузерным сценарием обновления списка во время незавершённого лайка.
- После смены/удаления сессии полный переход сбрасывает персональное состояние клиента и заново получает серверного пользователя. Обычные внутренние ссылки используют `Link`/router. Сохранение объявления на том же URL сохраняет полный переход для обновления серверного снимка и редактора.
- Только `no-img-element` отключён для явно перечисленных существующих медиакомпонентов в `eslint.config.js`: собственные варианты/srcset (#67), приватные API, SVG и локальные превью. Это не общее отключение правил Next и не замена медиаконвейера на `next/image`.

Регрессии: `effect-loading.spec.js` (поиск администратора, поздние успех/ошибка фильтра жалоб, переход к восстановлению пароля без смены документа), `gallery-interactions.spec.js` (очередь лайков и гонки витрины), `legal-editor.spec.js` (черновик без повторной загрузки при смене вкладок). Остальные сценарии мастера, карты, обсуждений и форм остаются в полном Chromium/WebKit-наборе.

## Минимальная матрица новой функции

Проверьте гостя, владельца, другого участника и заблокированного пользователя; для админского API — отсутствие роли и неверный Origin. Проверьте public → private, удаление родителя, повторный запрос, неправильный ID, пустой результат и сбой зависимости. Для файлов добавьте размер/формат, квоту, rollback/cleanup и запрет прямого доступа после скрытия.

Для карт тестируйте mock SDK и отсутствие лишних запросов, отдельно принимайте настоящую карту на разрешённом домене. Для достижений — размеры больших/сломанных изображений, редактирование текста, legacy PUT, приватность лидера и защиту связанных assets от удаления.

## CI и отчётность

### Форматирование (#144)

Из корня репозитория: `pnpm format` применяет форматирование, `pnpm format:check` только проверяет и возвращает ненулевой код при нарушении. CI выполняет `format:check` в Application/Resolver/HTTP после установки зависимостей и до lint. Остальные проверки и их строгость сохраняются.

Используется существующий Prettier из корневого lockfile (baseline: 3.9.9), настройки зафиксированы в `.prettierrc.json`: 80 колонок, два пробела, двойные кавычки, `semi`, `trailingComma: all`, LF. Встроенное форматирование языков внутри строк отключено, чтобы не переписывать SQL/HTML-данные. ESLint отвечает за корректность и не включает конфликтующих стилевых правил; дополнительный formatter/plugin не требуется.

Область проверки: поддерживаемые Prettier исходники JS/JSX/TS/MJS и CSS, JSON/JSONC-конфигурации, YAML workflows/Compose, Markdown документация — включая Resolver, scripts, tests и метаданные фикстур. `.prettierignore` исключает зависимости, сборки/отчёты/хранилища, сгенерированные version-файлы и MapLibre worker, lockfiles. HTML-ответы производителей и `archive-specification.json` в фикстурах Resolver сохранены как входные данные парсеров, включая пробелы; код fixture server и `source.json` проверяются. SQL, shell, Python, SVG, шрифты и другие бинарные данные не поддерживаются встроенными парсерами Prettier и остаются за существующими проверками, без массовых исключений исходного кода.

При изменении стиля сначала согласуйте конфигурацию, затем оформите чистое форматирование отдельным коммитом. Логические изменения должны быть видны отдельно. Проверка gate: временный JS-файл с `export const value={a:1}` должен провалить `pnpm format:check`; после `pnpm format` проверка должна пройти, затем пробный файл удаляется.

Единственный обнаруженный конфликт baseline с `no-unexpected-multiline` был в CSP e2e: Prettier переносил индексирование результата `headers()` на новую строку. Заголовок вынесен в переменную `policy`; проверка nonce и все CSP assertions сохранены, правило ESLint не отключалось.

`prepare` фиксирует SHA; Application/Resolver/HTTP, Chromium, WebKit mobile и Docker/backup проходят независимо. Итоговый `check` требует успеха каждой группы. Детали отмены и deploy находятся в [CI/CD](../operations/ci-cd.md).

В PR разделяйте: выполнено локально; выполнено CI с номером запуска; проверено вручную; пока не проверено. Для документационного PR достаточно отдельно проверить ссылки/структуру и назвать состояние автоматического CI, не выдавая чтение кода за runtime-тест.

## Проверки email-policy (#139)

`email-policy-http.js` проверяет прямые запросы без UI: все способы публикации, комментарии/ответы, контакт продавца, приватные черновики, снятие публичности и удаление; отдельно — заблокированную сессию и лимит повторной отправки. `email-policy.spec.js` проверяет сохранение формы после отказа и подтверждение почты без ухода со страницы.

Сценарии продукта явно используют `tests/fixtures/verified-user.js`: регистрация → захваченное письмо → настоящий endpoint подтверждения. Это не обход policy и не массовое изменение `email_verified_at` тестовой БД. Проверки регистрации, recovery и новой policy сохраняют неподтверждённых пользователей там, где это предмет теста. Production игнорирует mail capture; реальная доставка SMTP остаётся операторской проверкой.

### CSP

`tests/csp.test.js` проверяет настройки и очистку обоих форматов отчётов, `tests/csp-http.js` — настоящие заголовки/nonce, приёмник и лимиты. HTTP harness использует Report-Only, браузерный harness по умолчанию **enforce**, поэтому весь существующий Chromium/WebKit набор проверяет блокирующую политику; `tests/e2e/csp.spec.js` дополнительно проверяет отказ inline-script, доставку отчёта и разрешённый nonce. Не подменяйте приёмку живого Яндекса fixture SDK. Условия production enforcement — в [безопасности](../architecture/security.md#content-security-policy).
