# Проверки и тестовые окружения

[Оглавление](../README.md)

## Команды

Выполняются из корня репозитория после установки обеих групп зависимостей:

```bash
pnpm lint
pnpm typecheck
pnpm typecheck:tests
pnpm test:typecheck
pnpm test
pnpm build
(cd services/bike-resolver && npm run typecheck && npm test && npm run build)
pnpm test:integration
pnpm exec playwright install --with-deps chromium webkit
pnpm test:e2e
python3 scripts/test-compose.py
python3 scripts/test-deploy-images.py
bash scripts/test-backup-drill.sh
```

Команды — перечень уровней, не требование запускать тяжёлый полный drill после каждой правки текста. CI проверяет полный набор согласно [workflow](../../.github/workflows/check.yml). Узкую регрессию сначала запускайте адресно: `node --test tests/map-settings.test.js` или нужный Resolver fixture.

`test-deploy-images.py` проверяет доверие к run/attempt/main, ручной aggregate check, отказы для failed/fork/PR, digest/размер/состав архива, revision/platform и строгий SSH-протокол. Отдельные регрессии различают config digest и containerd daemon ID, требуют теги по проверенным daemon IDs и запрещают изменение любого production-тега при подмене конфигурации или ошибке экспорта. В operations после runtime drill режим `--docker SHA PATH_TO_IMAGES_TAR_GZ` упаковывает и проверяет ZIP, удаляет исходные теги, загружает реальные образы заново и проверяет config digests, стабильные IDs внутри одного daemon и запуск Node под project-scoped тегами обоих Compose файлов. Тот же архив повторно проходит этот тест в отдельном Docker daemon с явно включённым containerd image store. Это не заменяет проверку сети, свободного диска и установленных root-owned wrappers на production.

Регрессия `bike-week.spec.js` задерживает реальный ответ поиска и выдаёт его между pointer down/up на кнопке назначения: кнопка должна сохранить координату, PUT — завершиться успешно, UI — показать подтверждение. Тест не маскирует сдвиг увеличенным timeout или повторным кликом.

Бюджет браузерного CI job — 35 минут на установку браузера и системных пакетов, весь набор Playwright и загрузку визуальных artifacts. Полный WebKit-прогон занимает около 17,5 минуты, установка на медленном package mirror может превышать 8 минут; общий лимит учитывает оба этапа. Таймауты отдельных тестов и проверки Playwright задаются отдельно в конфигурации и spec-файлах.

`tsconfig.json` — единая strict-конфигурация Next и production TS/TSX (`strict`, DOM/Node/React, bundler resolution, `allowJs: false`). В `app/` и `lib/` нет обычных JS/JSX; временные JS-check configs и production baseline удалены. `pnpm check:production-ts` сканирует реальное дерево, включая untracked JS/JSX/MJS/CJS, и разрешает только точный путь генерируемого `lib/version.js` с контрактом `lib/version.d.ts`. Отрицательные пробы проверяют, что даже одноимённый `version.js` в других каталогах не проходит gate. Для shared `lib/**/*.ts` policy также проверяет прямой запуск Node 24 (`stripTypeScriptTypes`, mode `strip`); отрицательная проба запрещает синтаксис, требующий трансформации. Shared normalizer `services/bike-resolver/src/component-identity.ts` выполняется напрямую в Node unit/ops и компилируется независимым strict Resolver config. CLI использует TypeScript 7 через `@typescript/native`, Next/ESLint — совместимый API TypeScript 6 через npm alias `typescript`; см. [принципы](principles.md). Тесты доменных контрактов написаны на TypeScript и проверяются отдельным `tsconfig.tests.json` ([ниже](#типизированные-тесты-и-builders-283)); остальные тесты, scripts и configs сохраняют JS по практической пользе и не входят в production gate, а их lint/format/unit/HTTP/browser/runtime проверки сохраняются.

Отрицательные typecheck-пробы выполняются в отдельном временном дереве с копией app/lib/proxy/configs и отдельными compiler inputs, без incremental cache. Production-файлы рабочего checkout не изменяются. После очистки harness требует валидный typecheck временного дерева, отсутствие probe-каталогов в checkout и повторный обычный incremental typecheck production. Корневой proxy проверяется на неверный Request/вызов и возврат JS/JSX/MJS/CJS. `pnpm lint` дополнительно запускает [адресный Resolver gate](../../eslint.resolver.config.js) для `src/`: explicit any и TS suppressions запрещены; отрицательная lint-проба доказывает действие правил.

Для UI без изменений Resolver после production build можно запустить `node scripts/test-ui.js`. Harness поднимает disposable PGlite и Next на 3100, выполняет `gallery-interactions.spec.js` в Chromium и завершает процессы. Браузер должен быть установлен Playwright. Можно передать другие spec-файлы, `--project` и обычные параметры Playwright. Пример: `node scripts/test-ui.js tests/e2e/design.spec.js tests/e2e/navigation.spec.js tests/e2e/garage-polish.spec.js tests/e2e/gallery-interactions.spec.js`. Ни production БД, ни внешний парсер не используются. Unit-регрессии очереди реакций, URL и контраста: `node --test tests/gallery-interactions.test.js`.

## Что означает каждый уровень

| Уровень                 | Что доказывает                                                                                                                                                                                                                                                        | Чего не доказывает                                                           |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `pnpm lint`             | ESLint: правила хуков React, рекомендации Next, базовые ошибки JS и recommended TS/TSX rules. Ошибки и предупреждения блокируют CI (`--max-warnings=0`)                                                                                                               | Корректность логики и типов                                                  |
| `pnpm typecheck`        | Strict native TS/TSX в `app/` + `lib/` + `proxy.ts`, включая весь backend/API; запрет новых production JS. `test:typecheck` проверяет отрицательные API/DTO/null/TS/TSX/JS-policy/TS-lint пробы                                                                       | `scripts/`, оставшиеся JS-тесты и SQL-строки                                 |
| `pnpm typecheck:tests`  | Strict-проверка `tests/**/*.ts` и общего набора `tests/support` против настоящих production-типов: изменение DTO, строки БД или схемы ломает типы теста до запуска. Отрицательные пробы набора выполняет `test:typecheck`                                             | JS-тесты, scripts, e2e                                                       |

## Типизированные тесты и builders (#283)

Типы нужны там, где они ловят рассинхронизацию: тест, который читает строку БД, собирает тело запроса или разбирает DTO, должен перестать компилироваться, когда это меняется в production. Поэтому TypeScript выбран по пользе, а не по доле в статистике языков.

**Что написано на TS.** Общий набор `tests/support/` и тесты, которые напрямую проверяют доменные контракты. Покатушки: `ride-pulse`, `ride-intents`, `ride-matching`, `rides`, `ride-passport`, `ride-home`, `ride-agreements`, `ride-notifications`, `rides-market`. Рынок: `market-expiry`, `market-catalog`, `former-bikes-market`, `api-v1-market`. Каталог комплектующих: `component-catalog`, `component-community`, `component-products`. API v1: `api-v1-users`, `api-v1-journal`, `api-v1-rides`, `api-v1-search`, `api-v1-components`, `api-v1-write`, `api-v1-personal`. Остальное: `gamification`, `notification-email`, `notification-contract`, `notification-read-state`, `notification-settings`, `notification-fixtures`, `notification-docs`, `notification-grouping`, `notification-policy`, `notification-policy-settings`, `notification-email-policy`, `notification-fanout`, `notification-admin`, `bike-week`. Запускаются тем же `node --test` (Node снимает типы сам, ничего не собирается), `pnpm test` берёт `tests/*.test.js` и `tests/*.test.ts`. Миграция теста на TS — переименование и исправление типов, без смены сценариев и ожиданий; локальный PGlite и цикл по миграциям заменяет `testDatabase()`.

**Типы fixture-генераторов.** `tests/ride-fixtures.d.ts` и `tests/garmin-fixtures.d.ts` описывают JS-генераторы GPX/FIT/TCX/CSV, которые остаются общими с HTTP-сценариями и e2e: типизированные тесты получают контракт `(…) => string | Buffer`, а JS-потребители не меняются.

Builders принимают переопределения колонок (`Columns<Row>`) и возвращают строку так, как её читают сервисы. Типы строк — production: `lib/database-rows.ts` (для таблиц покатушек и уведомлений, у которых типа не было, добавлены `RideIntentRow`, `RideIntentWindowRow`, `RideRsvpRow`, `RideInvitationRow`, `NotificationRecord`, `BikeCommentRow`), `ListingInput`, `CurrentUser`, схемы API v1. Переданный `undefined` не затирает значение по умолчанию.

**Правила.** Не закрывайте ошибки через `any`, `@ts-ignore`, `@ts-expect-error`, `as unknown as`: ESLint запрещает suppression-комментарии. Негативный тест передаёт неверное значение через `invalid<T>()` или принимает `unknown`, а не ослабляет сигнатуру production-функции. Не расширяйте production-типы ради теста. Если тип показывает возможное отсутствие значения, это `present(…)` или явное сужение, а не `!`.

**Как изменение ловится.** `pnpm typecheck:tests` входит в CI рядом с `pnpm typecheck`. `test:typecheck` держит отрицательные пробы набора: колонка без поля, значение не того вида, черновик, который API отклонил бы, и «сырой» движок вместо `testDatabase()` не компилируются, а тест на builders компилируется.

**Что сознательно оставлено JS и почему.**

- `scripts/` (workers, миграции, операторские скрипты, `check-runtime`): это тонкие обёртки над TS-функциями `lib/` — циклы, аргументы и коды выхода. Их имена зашиты в Dockerfile (`COPY`), оба Compose (`command`), runtime-проверки, тесты, которые их запускают, и операторскую документацию; переименование ради типов тронуло бы упаковку без выигрыша в безопасности (логика уже типизирована в `lib/`). Пробный запуск `checkJs` по ним дал 18 замечаний, почти все — `catch (error)` без сужения и неявные параметры; осмысленных два: `chat-sync` читает `chat_jobs` без типа строки, а `cleanup-rides` обращается к полям объединения, которое `cleanupRides` описывает одним типом без дискриминанта. Это предмет отдельной правки типов в `lib/`, а не причина менять упаковку.
- `tests/e2e/` и конфигурации (`next.config.mjs`, ESLint, Playwright): Playwright сохраняется как есть; типы там не защищают доменные контракты.
- Оставшиеся `tests/*.test.js` (70 файлов: `api-v1`, `device-sessions`, `native-auth`, `identities`, `journal`, `community`, `social-core`, `bike-service`, `comment-threads`, `admin`, `showcase`, чистые функции и представления): они не запрещены и мигрируют по мере правки соседнего домена тем же переименованием; приоритет — тесты, читающие строки БД и DTO. Остальные JS-тесты, HTTP-сценарии и fixtures (`tests/*-http.js`, `tests/fixtures/`): HTTP-тесты работают через `fetch` с JSON и проверяют границу, а не внутренние типы; перенос по мере изменения соседнего домена, а не массовым rename.

## База и изоляция

[Integration harness](../../scripts/test-resolver-integration.js) создаёт собственные временные БД/каталоги и запускает fixture Resolver. При `TEST_DATABASE_URL` используется отдельный PostgreSQL с правами создания тестовой БД. **Не передавайте production connection string.** Без этой переменной локальный harness может использовать одно соединение disposable PGlite; concurrency-тесты требуют настоящий PostgreSQL.

`tests/community-concurrency.js` удерживает транзакцию лайка после блокировки велосипеда, запускает комментарий на другом соединении и через `pg_blocking_pids` подтверждает пересечение запросов. После освобождения оба запроса должны завершиться, сохранив комментарий и два уведомления. Это регрессия взаимной блокировки: операции соблюдают порядок `users → bikes`, включая внешние ключи уведомлений. Тест подключён к HTTP-набору при использовании PostgreSQL.

В браузерной проверке карты ответы тайлов задерживаются до измерения предпросмотра; затем проверяются неизменная высота, наведение на график и сохранение canvas при прокрутке. Обзор всех страниц открывает каждый URL и тему в отдельном browser context со снимком настоящей подтверждённой сессии: cookie/storage предыдущих страниц не влияют на следующий визуальный сценарий. Каждый сценарий дополнительно проверяет пользователя через `/api/me`. Ошибки JavaScript продолжают проверяться; переходы, история, сохранение сессии и восстановление прокрутки покрыты отдельными сценариями. `ride-passport` проверяет позднее событие `close` вложенной панели: оно не должно возвращать фокус с уже выбранного следующего поля.

Браузерные тесты меняют настройки сайта, поэтому `workers:1` и отсутствие внутреннего fullyParallel — часть изоляции. CI распараллеливает браузеры по **разным** runners и БД, а не по общей базе. Артефакты разных браузеров/attempt имеют разные имена.

Backup drill создаёт собственные Compose projects и удаляет только их. Это не команда для проверки восстановления поверх рабочего проекта `cola`.

Редактор объявления проверяется с намеренно задержанной загрузкой JavaScript (#162): все SSR-поля и действия заблокированы до гидратации, затем первый ввод сохраняется, фотография получает HTTP 201 и объявление публикуется. Это воспроизводит гонку раннего ввода без случайных задержек, повторов теста или увеличения таймаутов.

Зависимости эффектов описывают реальные причины обновления: идентификатор пользователя, страницу и фильтры, примитивные поля модели. Ответы списков проверяют ревизию запроса; поиск пользователей читает текущий черновик при отправке формы или переходе страницы, без запроса на каждую букву. - `useBikeReaction` сохраняет одну очередь запросов на велосипед и пользователя, даже если список вернул новый объект того же велосипеда. Локальное исключение `exhaustive-deps` защищено браузерным сценарием обновления списка во время незавершённого лайка.
- После смены/удаления сессии полный переход сбрасывает персональное состояние клиента и заново получает серверного пользователя. Обычные внутренние ссылки используют `Link`/router. Сохранение объявления на том же URL сохраняет полный переход для обновления серверного снимка и редактора.
- Только `no-img-element` отключён для явно перечисленных существующих медиакомпонентов в `eslint.config.js`: собственные варианты/srcset (#67), приватные API, SVG и локальные превью. Это не общее отключение правил Next и не замена медиаконвейера на `next/image`.

Регрессии: `effect-loading.spec.js` (поиск администратора, поздние успех/ошибка фильтра жалоб, переход к восстановлению пароля без смены документа), `gallery-interactions.spec.js` (очередь лайков и гонки витрины), `legal-editor.spec.js` (черновик без повторной загрузки при смене вкладок). ## CI и отчётность

### Форматирование (#144)

Из корня репозитория: `pnpm format` применяет форматирование, `pnpm format:check` только проверяет и возвращает ненулевой код при нарушении. CI выполняет `format:check` в Application/Resolver/HTTP после установки зависимостей и до lint. Остальные проверки и их строгость сохраняются.

Используется существующий Prettier из корневого lockfile (baseline: 3.9.9), настройки зафиксированы в `.prettierrc.json`: 80 колонок, два пробела, двойные кавычки, `semi`, `trailingComma: all`, LF. Встроенное форматирование языков внутри строк отключено, чтобы не переписывать SQL/HTML-данные. ESLint отвечает за корректность и не включает конфликтующих стилевых правил; дополнительный formatter/plugin не требуется.

Область проверки: поддерживаемые Prettier исходники JS/JSX/TS/MJS и CSS, JSON/JSONC-конфигурации, YAML workflows/Compose, Markdown документация — включая Resolver, scripts, tests и метаданные фикстур. `.prettierignore` исключает зависимости, сборки/отчёты/хранилища, сгенерированные version-файлы и MapLibre worker, lockfiles. HTML-ответы производителей и `archive-specification.json` в фикстурах Resolver сохранены как входные данные парсеров, включая пробелы; код fixture server и `source.json` проверяются. SQL, shell, Python, SVG, шрифты и другие бинарные данные не поддерживаются встроенными парсерами Prettier и остаются за существующими проверками, без массовых исключений исходного кода.

При изменении стиля сначала согласуйте конфигурацию, затем оформите чистое форматирование отдельным коммитом. Логические изменения должны быть видны отдельно. Проверка gate: временный JS-файл с `export const value={a:1}` должен провалить `pnpm format:check`; после `pnpm format` проверка должна пройти, затем пробный файл удаляется.

Единственный обнаруженный конфликт baseline с `no-unexpected-multiline` был в CSP e2e: Prettier переносил индексирование результата `headers()` на новую строку. Заголовок вынесен в переменную `policy`; проверка nonce и все CSP assertions сохранены, правило ESLint не отключалось.

`prepare` фиксирует SHA; Application/Resolver/HTTP, Chromium, WebKit mobile и Docker/backup проходят независимо. Итоговый `check` требует успеха каждой группы. Детали отмены и deploy находятся в [CI/CD](../operations/ci-cd.md).

В PR разделяйте: выполнено локально; выполнено CI с номером запуска; проверено вручную; пока не проверено. Для документационного PR достаточно отдельно проверить ссылки/структуру и назвать состояние автоматического CI, не выдавая чтение кода за runtime-тест.

## Проверки email-policy (#139)

`email-policy-http.js` проверяет прямые запросы без UI: все способы публикации, комментарии/ответы, контакт продавца, приватные черновики, снятие публичности и удаление; отдельно — заблокированную сессию и лимит повторной отправки. `email-policy.spec.js` проверяет сохранение формы после отказа и подтверждение почты без ухода со страницы.

`identities.test.js` проверяет протокол Яндекс ID на подмене сети, `identities-http.js` — весь вход, привязку и отказы на реальном сервере с подменой Яндекса (`tests/fixtures/yandex-provider.js`, включается `COLA_YANDEX_FIXTURE=1` только в харнессе). Настоящий Яндекс эти проверки не подтверждают.

Сценарии продукта явно используют `tests/fixtures/verified-user.js`: регистрация → захваченное письмо → настоящий endpoint подтверждения. Это не обход policy и не массовое изменение `email_verified_at` тестовой БД. Проверки регистрации, recovery и новой policy сохраняют неподтверждённых пользователей там, где это предмет теста. Production игнорирует mail capture; реальная доставка SMTP остаётся операторской проверкой.

### CSP

`tests/csp.test.js` проверяет настройки и очистку обоих форматов отчётов, `tests/csp-http.js` — настоящие заголовки/nonce, приёмник и лимиты.
