# Принципы архитектуры и разработки

[Оглавление](../README.md)

## До изменения

Сформулируйте пользовательский сценарий и инварианты: кто владелец, что увидит гость, как закрывается доступ, что происходит при повторном запросе и отказе внешнего сервиса. Найдите существующий путь выполнения и тест. Один PR должен иметь понятную цель; рефакторинг соседнего UI или инфраструктуры не добавляется незаметно к исправлению парсера.

## Распределение ответственности

HTTP-обработчик отвечает за маршрут, пользователя/Origin, входную схему, ограничения и статус ответа. Правила и SQL живут в `lib`, а парсинг сайтов — в `services/bike-resolver/src`. Клиентский компонент управляет черновиком и представлением, но не решает, разрешена ли публикация и какой пользователь является владельцем.

Используйте существующие `transaction(q => ...)`, DTO, обработчики файлов и квот. Не создавайте второй механизм сессий, вторую ленту или отдельный каталог только ради одного экрана. `factory_spec`, текущие компоненты и journal snapshots не объединяются в одно поле: они отражают разные состояния.

## API и данные

Входные параметры валидируйте на сервере. SQL-значения передавайте параметрами; имена таблиц могут выбираться только из закрытого серверного набора. Новое публичное поле добавляйте в явный DTO и отдельно проверяйте приватный ответ.

Новый production-код под `app/` и `lib/` — `.ts/.tsx` с `strict` из [tsconfig.json](../../tsconfig.json). Пока идёт #256, `allowJs` позволяет импортировать legacy-модули, но не отключает проверку TS. Отдельные [jsconfig.json](../../jsconfig.json) и [jsconfig.strict.json](../../jsconfig.strict.json) сохраняют прежние `checkJs` для `lib/` + `app/api/` и `strictNullChecks` для `lib/`. `pnpm typecheck` выполняет все три проверки и [policy](../../scripts/check-production-typescript.js), которая запрещает новые JS/JSX/MJS/CJS в production. Зафиксированный [baseline](../../scripts/production-js-baseline.json) только сокращается по мере миграции; единственное дополнительное исключение — генерируемый `lib/version.js`. Массовый rename и поведенческие изменения выполняются в разных этапах/коммитах.

Общие экспортируемые типы — [lib/contracts.ts](../../lib/contracts.ts): `CurrentUser`/nullable `Viewer`, сериализованный `ViewerDto`, `PublicAuthor`/`PublicProfile`, ID/reference, API errors/pagination и публичные bike/component/photo DTO. Legacy JSDoc реэкспортирует эти типы по прежним путям, а native TS использует `import type`, чтобы серверные модули не попадали в клиентский runtime. Типы ввода выводятся через `z.infer` из существующих схем; типы не заменяют runtime-проверку. Списки полей публичных DTO сверяются с типом в обе стороны; поле вне типа, например `email` у автора, не пройдёт проверку. JSON читается как `unknown`, viewer и repository results допускают `null`. Остальной legacy SQL/JS пока не имеет полного `strict`/`noImplicitAny`; его покрытие не следует выдавать за завершённую миграцию.

Используйте простые interfaces/unions/generics; не накапливайте `any`, `@ts-ignore`, `@ts-nocheck`, `@ts-expect-error` или `as unknown as` для обхода проверки. ESLint поддерживает TS/TSX, сохраняет React/Next правила и запрещает explicit `any` и suppression comments. `pnpm test:typecheck` проверяет отрицательными пробами старые API/DTO/null gates, новый strict TS/TSX, запрет нового production JS и TS lint. Относительные импорты сохраняются; новый alias не требуется для миграции. Перенесённые shared-модули импортируются с явным `.ts`: Node 24 исполняет их напрямую в tests, scripts и Docker ops через type stripping. `allowImportingTsExtensions` включён в native и legacy конфигурациях. Policy вызывает `stripTypeScriptTypes` в режиме `strip` для `lib/**/*.ts`; отрицательная проба отклоняет синтаксис, требующий трансформации (например parameter properties). `import type` не создаёт runtime-зависимостей.

Строки PostgreSQL описаны в `lib/database-rows.ts`: bigint/numeric остаются строками, даты — `Date`, nullable-колонки — nullable. `Queryable.query<Row>()` возвращает `QueryRows<Row>`; без контракта поля имеют тип `unknown`. Legacy JS использует JSDoc на границе конкретного SQL-запроса. Первая часть #258 переносит общую инфраструктуру, bikes/catalog/factory, community/chat, journal/market, gamification и site/helpers. Rides/activity imports и HTTP routes остаются на legacy gates до второй части #258.

CLI `tsc` остаётся TypeScript 7.0.2 (`@typescript/native` — npm alias). Next и typescript-eslint используют API из `typescript` → `@typescript/typescript6` 6.0.2: TypeScript 7 пока не предоставляет совместимый API. Это [официальный режим совместного использования](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-6.0), а не отключение build typecheck. Не меняйте aliases на один compiler без проверки lint, Next build и отрицательных проб. Resolver сохраняет свою независимую конфигурацию и compiler.

Повторные лайки/подписки должны оставаться идемпотентными. Для квот необходима сериализация конкурентных изменений, не только проверка перед INSERT. Не доверяйте переданным клиентом метрикам GPX, заводскому результату или принадлежности дочернего объекта.

Для новой SQL-миграции: новый файл в `db/`, регистрация в явном списке [scripts/migrate.js](../../scripts/migrate.js), тест чистой установки и обновления существующей БД. Применённые версии не переписываются. Настройки расширяйте необязательными полями/defaults, сохраняя старые значения при совместимых запросах. Изменения schema и восстановление проверяются вместе; см. [данные](../architecture/data-model.md).

## Парсер

Разделяйте поиск кандидата, подтверждение модели/года, сетевое получение, извлечение и нормализацию. При недостатке данных возвращайте partial/ambiguity/error, а не правдоподобные выдуманные детали. Не подставляйте запрошенный год как год источника. Сохраняйте raw values и provenance; результаты разных моделей не смешиваются.

Любое изменение сайта-источника оформляйте fixture-тестом с положительным и ложноположительным примером. Сетевой 403 и отсутствие спецификации — разные неисправности. Не добавляйте browser/LLM или обход антибота как скрытый fallback. Подробнее: [расширение Resolver](../resolver/sources.md).

## Интерфейс

Общие карточки, встроенные векторные иконки, `SiteProvider`, `PromptComposer` и существующие формы предпочтительнее новых несвязанных реализаций. Поддерживаемые настройки темы, контента и поведения должны сохраняться. Размер иллюстрации и фото ограничивайте разными контейнерами: селектор вроде `.card img { height:100% }` не должен растягивать вложенные иконки. Для локальной вёрстки используйте CSS Module/ограниченный selector.

Тяжёлые части, которые нужны не каждому посетителю, подключайте через `next/dynamic`: мастер велосипеда (схемы zod), поиск фото, заводскую спецификацию, обсуждение, редактор Tiptap (`PromptComposer` в обсуждении и статьях), редактор журнала, форму входа. Форматированный текст для чтения приходит с сервера уже разобранным (`bodyDoc`), поэтому `RichTextBody` не тянет парсер. Бюджет сжатого JS гостя проверяет `tests/e2e/bundle-budget.spec.js`; при превышении тест называет самые крупные чанки, а для записи, статьи и комментариев проверяет, что гость не получает код ProseMirror. Схемы из `lib/validation.ts` в клиентском коде используйте только в лениво загружаемых частях (как в мастере), иначе zod попадает в бандл гостя.

Состояния loading/empty/error/success обязательны. У асинхронного эффекта должна быть защита от позднего результата после ухода со страницы. У каждого действия — доступное имя, keyboard focus и touch-сценарий; анимации уважают reduced motion. См. [UI](ui.md).

## Что включить в PR

Опишите поведение до/после, изменённые границы доступа и данные, выполненные команды и ограничения проверки. Для UI приложите desktop/mobile примеры; для источника — fixture и различие между offline parsing и live availability. Для миграции укажите порядок выкладки и безопасное восстановление. Не пишите «все тесты проходят», если выполнена только проверка синтаксиса.

Работайте в отдельной ветке, не выполняйте merge/deploy за владельца без запроса. Проверяйте feature-код локально и в CI. Изменения workflows, root-owned wrappers, Dockerfile, сетевых разрешений и secrets требуют отдельного review: тесты не превращают такой код в безопасный sandbox.

Документация модуля обновляется в том же PR. Нереализованные идеи помечайте как план, не как существующий контракт.
