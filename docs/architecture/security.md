# Безопасность и приватность

[Оглавление](../README.md)

## Что защищает приложение

[auth.js](../../lib/auth.js) создаёт случайный session token, хранит его SHA-256 digest и выдаёт `cola_session` с HttpOnly, SameSite=Lax и настраиваемым Secure. Пользователь и его текущая блокировка/роль читаются из базы. Пароли хешируются scrypt в [password.js](../../lib/password.js); неизвестный email не должен превращать вход в быстрый обход проверки. Регистрация не назначает admin.

Мутации проверяют Origin относительно `APP_ORIGIN`, пользовательские операции — владельца, административные — роль. Ограничения частоты находятся и в приложении, и в production nginx. Наличие доступа к админке не делает пользовательские API универсальным просмотром чужих приватных данных.

## Публичные границы

DTO собираются явно; не возвращайте `SELECT *` наружу с удалением нескольких известных секретов. Для поездки, записи журнала, обсуждения, ленты, поиска и уведомления проверяется текущая доступность базового объекта. Приватный велосипед закрывает связанную публичную выдачу. Сохранение ссылки и подписка не дают дополнительного разрешения.

Публичность цены — отдельная настройка. Нельзя использовать скрытую цену в публичном рекорде или вернуть её через снимок детали. Для GPX клиент получает уже разрешённую геометрию; renderer не восстанавливает разрывы и скрытые начало/конец. Полные метрики поездки могут сохраняться при урезанной публичной геометрии — это нужно объяснять пользователю.

Защищённые фото, аватары и journal media выдаются через свои API, а не статический каталог nginx. Перепроверка доступа не отзывает байты, которые посетитель успел скачать раньше.

## Файлы и внешние страницы

Изображения проходят ограничения размера и декодирование/нормализацию. Обычные фото и точный lossless-путь UI-иконок — разные обработчики. Пути файлов формируются сервером; имя из ZIP/загрузки не становится путём записи. Нельзя включать SVG-исполнение ради удобства импорта.

Resolver применяет публичные адреса, проверку DNS/IP, pinning, проверку редиректов, allowlist официальных адаптеров и blocklist ручных источников. HTML/JSON извлекаются как данные, не исполняются. Ручная ссылка пользователя не освобождает от SSRF-защиты. Ошибка 403/challenge не является разрешением обходить защиту источника.

## Секреты и настройки

`DATABASE_URL`, `POSTGRES_PASSWORD`, `BIKE_RESOLVER_TOKEN`, `TRUSTED_PROXY_KEY` — серверные значения. Публичный ключ карт, наоборот, виден браузеру и ограничивается у провайдера. Не помещайте OAuth secret или внутренний адрес в публичные site settings.

Приватный proxy key позволяет доверять `X-Cola-Client-IP` только от настроенного nginx. Произвольный `X-Forwarded-For` не должен менять rate-limit identity. Не включайте real-IP доверие ко всем адресам. Не публикуйте `docker compose config` с раскрытыми значениями, целый nginx-конфиг или auth headers в PR.

## Граница доверия CI и deploy

Hosted CI и self-hosted deploy разделены. У runner нет необходимости состоять в группе Docker; ему разрешается соответствующий root-owned wrapper. **Это ограничение интерфейса, а не sandbox для недоверенного кода.** Wrapper не проверяет CI криптографически: происхождение проверенного SHA обеспечивается workflow, а production wrapper дополнительно сравнивает его с текущим `origin/main`.

Код из `main`, workflow, Dockerfile, миграции, env и серверный checkout должны считаться привилегированными. Staging берёт Compose из `main`, но запускает код выбранной ветки и не подходит для произвольного враждебного PR. На staging не должно быть production secrets/данных. Не доверяйте collaborator только на основании того, что ему предложено «не пушить в main»; правила ветки и review настраиваются в GitHub отдельно.

Официальная справка: [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use).

## Известные ограничения

Email verification, password recovery и OAuth не реализованы в проверенном snapshot. CSP ограничивает framing/base/object, но не является полной allowlist для script-src. Квота одного пользователя не ограничивает общий размер сайта. Файлы и БД требуют backup и cleanup. Проверки fixture не доказывают доступность внешнего сайта или абсолютную безопасность. Подключение новых провайдеров, публикация репозитория и открытая регистрация требуют отдельной оценки данных и доступа.
