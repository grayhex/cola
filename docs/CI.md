# CI: параллельные проверки без лишних прогонов

`CI · ColaBike` сохраняет полный набор проверок. После короткого `prepare`
параллельно работают четыре тяжёлые задачи:

| Задача | Что проверяет |
| --- | --- |
| Application, Resolver and HTTP | Unit/DB, сборка приложения, тесты и сборка Resolver, HTTP integration на PostgreSQL 17, включая конкурентные квоты |
| Browser · chromium | Все сценарии проекта Chromium |
| Browser · webkit-mobile | Все сценарии проекта мобильного WebKit |
| Docker and backup restore | Compose и полный disposable backup/restore drill |

`prepare` один раз разрешает запрошенный ref в SHA. Все задачи получают именно
этот коммит, даже если ветка ручного запуска обновилась в процессе проверки.
Итоговый job **check** остаётся единственным обязательным статусом для branch
protection. Он требует `success` от всех групп, включая обе browser matrix jobs;
ошибка, отмена или пропуск обязательной группы блокируют успешное завершение.

## Изоляция и ресурсы

Каждый browser job имеет собственный runner, PostgreSQL, приложение и временное
хранилище. Существующий integration harness создаёт отдельную БД и каталоги,
запускает fixture Resolver и выполняет cleanup. Порты между jobs не конфликтуют.
Внутри Playwright остаются `workers: 1` и `fullyParallel: false`: тесты меняют
общие настройки сайта, поэтому делить одну БД между параллельными тестами нельзя.

CI создаёт временную обёртку над `playwright.config.js` **после сборки**, выбирая
ровно один именованный проект и сохраняя остальные параметры. Неизвестное или
неоднозначное имя приводит к ошибке, а не к успешному прогону без тестов.
Это работает и при ручной проверке старых refs: их harness и исходная конфигурация
не обязаны поддерживать новые CLI-аргументы или переменные выбора браузера.
Локальный `pnpm test:e2e` не изменён и по-прежнему запускает оба проекта.

В каждой browser job устанавливается только её браузер. Unit/Resolver-тесты там
не повторяются. Короткая сборка приложения выполняется на каждом runner отдельно:
передача большого `.next`-артефакта сейчас намеренно не добавлена. Docker-сборка
в backup drill остаётся самостоятельной проверкой production-упаковки.

Скриншоты и traces: артефакты `browser-review-chromium-<attempt>` и
`browser-review-webkit-mobile-<attempt>`, хранение 7 дней. При обычном падении
тестов они сохраняются; отменённые прогоны не задерживаются ради выгрузки.
Падение одного браузера не отменяет другой, чтобы сохранить обе диагностики.

## Какие прогоны отменяются

- Новый commit в PR отменяет предыдущий CI того же PR.
- Новый push в `main` отменяет предыдущий CI ветки `main`.
- Событие закрытия/merge PR отменяет его оставшийся CI через ту же concurrency
  group. Вместо тестов выполняется только короткий job-подтверждение закрытия.
- Разные PR не отменяют друг друга. На feature-ветки нет отдельного push-trigger:
  они проверяются по PR, без дублирующего branch-push запуска.
- Ручные запуски, в том числе CI из production/staging workflow, изолированы по
  `run_id`. Они не отменяют вызвавший их workflow во время возможного deploy.

Проверка PR и проверка итогового commit после merge **не взаимозаменяемы**:
автоматический production deploy по-прежнему ждёт успешный CI события `push`
в `main` и получает его точный SHA. Новая проверка CI не прерывает активный deploy.
Production сохраняет `concurrency: cola-production`, `cancel-in-progress: false`,
root-owned wrapper и отказ от устаревшего/non-main SHA. `workflow_run` дополнительно
фильтруется по `main`, чтобы не создавать лишние deploy-запуски для feature-веток.

Существующие прогоны старой версии workflow не получают новую concurrency group
задним числом. Автоматическая отмена действует для запусков обновлённого workflow.

## Объём изменения

Тесты по типу файлов не пропускаются; path-фильтров, увеличения числа workers,
публикации образов и переноса сборки с VPS в registry в этом изменении нет.
Настройки runner, секреты, Dockerfile и серверный deploy-скрипт менять не нужно.
В branch protection нужно сохранить required check **check**.

Сравнивать скорость следует по нескольким успешным запускам и полному времени
от push до завершения CI: очередь runner и установка браузеров тоже учитываются.
Четыре параллельных runner сокращают ожидание, но сами по себе не гарантируют
уменьшения суммарных оплачиваемых runner-минут.
