# Работа в ColaBike

Общие инструкции для Astra-6, Opus 5.5 и других агентов. Читайте только главы, нужные для задачи: [карта документации](docs/README.md).

## Контекст

- Next.js / React; production-код в `app/` и `lib/` — native strict TypeScript/TSX; бизнес-логика и SQL в `lib/`, HTTP в `app/api/`, UI в `app/ui/`. Общие типы границ — `lib/contracts.ts`; входные типы выводятся из Zod. Resolver — отдельный TypeScript-сервис в `services/bike-resolver/`.
- Node 24.x; корень — pnpm с закреплённым `packageManager`, Resolver — npm. Сохраняйте соответствующие lockfiles. Код, схема и workflows определяют текущее поведение; issues — намерения и приоритеты.
- Интерфейс: [дизайн-код](docs/development/design-system.md), семантические токены `app/styles/tokens.css`, общие компоненты. Обе темы, мобильный экран, клавиатура и reduced motion обязательны. Переиспользуйте существующие Motion/Rive-механизмы.

## Инварианты

- Авторизацию, владение и приватность проверяйте на сервере при каждом чтении и изменении. Не раскрывайте email, секреты, приватные медиа или скрытые координаты через DTO, поиск, кеши и логи.
- Новая миграция: `db/` + списки в `scripts/migrate.js` и `scripts/test-db.js`. Применённые версии не переписывайте; номер `013` не переиспользуйте. Тесты работают только с изолированными данными.
- Внешние интеграции необязательны: отказ Resolver сохраняет ручной ввод; отключение провайдера не должно ломать основной сайт. Не обходите ограничения источников и серверную валидацию.
- Docker `runner` — web; `ops` — миграции и workers; backup/restore — из checkout на хосте. При изменении упаковки сверяйте Dockerfile, `.dockerignore`, оба Compose и runtime-проверки.

## Выполнение

- Работайте в отдельной ветке от актуального `main`, соблюдайте границы задачи. Не затирайте чужие изменения. Merge и production deploy — только с явным разрешением владельца: merge запускает автоматическую выкладку.
- Во время работы запускайте адресные проверки. Перед PR проверьте итоговый diff и соответствующие gates из [руководства по тестированию](docs/development/testing.md); не ослабляйте CI ради зелёного статуса. Для UI проверяйте результат в браузере.
- Обычные JS/JSX/MJS/CJS под `app/` и `lib/` запрещены hard gate `pnpm typecheck`; единственное исключение — генерируемый `lib/version.js` с контрактом `lib/version.d.ts`. Не закрывайте типовые ошибки через `any`, `@ts-ignore`, `@ts-nocheck` или цепочки casts; сохраняйте runtime validation и серверные проверки доступа.
- Обновляйте действующую главу вместе с поведением; новую главу включайте в `docs/README.md` и `docs/book.json`. Не коммитьте секреты, пользовательские выгрузки, отчёты прогонов и разовые планы.
- В PR кратко: проблема, результат, проверки, риски. Отдельно указывайте, что не удалось проверить; fixture-тест не подтверждает работу внешнего сервиса в production.
